## The defect (verified live, reproduced by test)

Sweep #1 claimed `Sanmoo/my-tasks#53` and died between the claim and the spawn:
the tracker held the claim (label `agent-claimed`), the registry dir existed and
was empty — no `log-*.jsonl`, no `sessao/`, no `desfecho.json` (zero footprint).
Every later sweep, including `--once`, derived the work as **held (idle)**:
`deriveUnreconciledFall` had an explicit branch for `lastAttempt === 0` that
returned `idle`, the pool excluded claimed works, and nothing launched — an
orphan held forever, contradicting spec story 22 ("processos órfãos tratados
como queda abrupta").

## The semantics implemented

The derivation is stateless — it cannot see the process. The sweep engine knows
its in-flight launches (`Slots.workKeys`: work keys claimed/launched by THIS
process and not yet collected), and now hands that set into the derivation:

- `SweepEngine.deriveAndAct` (src/loop.ts) computes `inFlight: Set<string>`
  (format `"<repo>#<n>"`, same as `workKey`), keeps using it to filter
  in-flight works out of the reserved scan (a running worker is its own
  state; the tick does not re-launch it nor act on a terminal state
  mid-flight — unchanged), and additionally passes the set as a new optional
  5th parameter to `deriveReserved` (src/state/derive.ts).

- `deriveUnreconciledFall` now distinguishes the two honest readings of a
  claim with **zero attempt evidence** (`readReconciliationFacts` →
  `{ lastAttempt: 0, consecutiveFall: false }`):

  | zero-footprint claim | in the engine's in-flight set? | derivation |
  |---|---|---|
  | this process is between the claim and the worker's first write | **yes** | `idle` — held (previous behavior, preserved) |
  | no process holds the launch (a death between claim and spawn — orphan) | **no** | `fall` → **release** (abrupt fall, story 22) |

- **Exact zero-footprint counting semantics:** the empty registry is read
  honestly — `readReconciliationFacts` on an empty dir reports
  `lastAttempt: 0` and `consecutiveFall: false`, which the existing ruler
  reads as **attempt 1 with no previous fall**. The orphan is therefore a
  **1st fall → release** (`claimed`→`ready` back on the tracker, branch
  preserved). This matches story 17: releasing devolves the work to the
  pool, and the same `--once` sweep re-claims it and launches it as
  attempt 1 (`readLaunchFacts` on the empty dir → `attempt: 1,
  previousFall: false`). A zero-footprint orphan can never derive
  `block` (that needs `consecutiveFall`, which requires evidence of prior
  attempts). If the re-claim falls again WITH a footprint (logs, no record),
  the normal consecutive-fall counting applies (2nd → blocked + comment).

- Claims WITH attempt evidence (logs without a record, records, etc.) are
  untouched — the previous ruler applies exactly as before.

- The claim-and-die-again zero-footprint cycle (orphan → release → re-claim
  → death pre-spawn → orphan) still counts as 1st fall each time (the disk
  honestly has zero evidence to count with); each cycle is a visible
  release on the tracker rather than a silent freeze. Chosen per the task's
  guidance ("probably attempt 1 → release; that's fine and matches story 17").

## Residual risks

- **Claim-without-dir window (out of scope, pre-existing):** a crash after
  the tracker claim write but before `launchAndCollect`'s `mkdirSync` leaves
  a claimed issue with NO registry dir. `scanReservedWorks` (WHO is reserved)
  is dir-driven, so that orphan stays invisible to the derivation too.
  Narrow (one instruction after an async tracker write), but real. A cheap
  follow-up: create the registry dir BEFORE the claim (an empty dir on a
  ready work is harmless — the pool re-claims and reuses it).
- **Cross-process races on one workspace:** two engines on the same
  workspace are not coordinated (by design, stateless); a second sweep will
  fall-and-pick-up another live process's zero-footprint launch. Single
  engine per workspace remains the operating assumption.
- A zero-footprint orphan loop (claim → die pre-spawn → release → re-claim →
  …) never escalates to `blocked`, because the disk carries no evidence to
  count consecutive falls from. Each cycle is visible on the tracker
  (release/re-claim) rather than silent.
