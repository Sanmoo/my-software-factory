# Ticket 16 follow-up: robust local `credential.helper` write (exit-5 fix)

## Symptom (from the real smoke)

The push/PR phase failed at `git config --local credential.helper ""` with
exit 5:

```
warning: credential.helper has multiple values
error: cannot overwrite multiple values with a single value
```

Cause: the clone's LOCAL config held multiple `credential.helper` entries.
The clone step itself bakes two (`--config credential.helper=` + the gh
helper), and a reused clone (one clone per repo, reused across works)
accumulates entries — plus the machine's odd git config (the broken mac
leftover global helper seen in ticket 17's proof). A bare `git config --local
credential.helper <value>` on a multivar is refused (exit 5). Reproduced
locally against git in the test pre-state (see tests below).

## Call sites changed

Only one code site writes/read the clone's local `credential.helper` — the
bake step inside `pushBranch` of the GitHub adapter. `git config` now appears
nowhere else in `src/` (grep `credential.helper` confirms; `src/git/local.ts`
only mentions the helper in a comment).

1. `src/tracker/github-adapter.ts`
   - New exported `bakeCredentialHelper(cloneDir, env, runner)` — the whole
     bake, extracted from `pushBranch` so it is testable offline against real
     git. Behavior:
     - `git config --local --unset-all credential.helper` — tolerating exit 5
       (key absent = nothing to unset);
     - `git config --local --unset-all credential.https://github.com.helper` —
       same tolerance;
     - then a single set: `credential.helper = ""` (the ambient-wipe empty
       value that resets system/global helpers read so far) and
       `credential.https://github.com.helper = !gh auth git-credential`.
     - End state on ANY clone (fresh or reused): exactly ONE
       `credential.helper` value and exactly ONE URL-scoped helper value.
   - `pushBranch` now calls `bakeCredentialHelper(cloneDir, env, this.runner)`
     instead of the three bare sets.
   - The clone command itself is unchanged (it must bake a helper at clone
     time to authenticate the private clone; the bake's unset-all cleans its
     two entries right after).

Read tolerance: there was no application-level READ of `credential.helper`
anywhere in `src/` (the smoke failure's warning came from git's own
bare-set-on-multivar path). The bake now touches the keys only through the
multivar-safe forms (`--unset-all` / `--get-all`), so git's "has multiple
values" warning can never break behavior; the fake-runner path additionally
proves a failure with exit code 5 during the unset is tolerated.

## Tests added (all offline, `src/tracker/github-adapter.test.ts`)

New describe: "9c. credential bake: a reused clone with accumulated helpers
ends with exactly one":

1. **pre-state proof**: a fixture clone whose local config holds TWO+
   `credential.helper` values — the bare set the smoke used rejects with
   exit code 5 (reproduces the ticket offline).
2. **the fix**: after `bakeCredentialHelper` on that same fixture, `--get-all
   --null` shows exactly ONE `credential.helper` value (the ambient-wipe
   empty one) and exactly ONE `credential.https://github.com.helper`
   (`!gh auth git-credential`); the flow does not throw exit 5.
3. **absent-key tolerance**: the bake on a pristine repo with no helper keys
   at all (unset-all exits 5) succeeds and bakes exactly one value.
4. **adapter ordering**: `pushBranch` (fake runner simulating exit 5 on every
   unset-all, as real git does on an absent key) still completes; the set
   comes only after the unset-all and the intended helper is still baked.

## Residual risks

- The bake guarantees a clean LOCAL config; a global/system helper (e.g. the
  mac leftover) is still neutralized only by the ambient-wipe empty value
  ordering — same semantics as before, unchanged.
- If the machine's git predates `--unset-all` multivar semantics (any git in
  the last decade), not covered — out of scope.
